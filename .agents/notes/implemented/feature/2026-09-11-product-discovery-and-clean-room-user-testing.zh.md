# Agent Note: 产品发现与净室用户测试

Status: implemented

[English](2026-09-11-product-discovery-and-clean-room-user-testing.md) | 中文

## 问题

实现优先的编码 Agent 可以高效构建用户要求的功能，却可能没有先确认真实用户问题是否存在、现有替代方案是否已经满足需求，或者哪个小型实验可以证伪产品想法。继承产品讨论的 teammate 会遇到相反的评估问题：它知道预期工作流，容易解释或维护设计，而不是发现首次用户实际看到的内容。

## 决策

除非用户要求直接执行，`flash-first` Prompt Profile 与实验性 Agent Teams 策略会把产品发现视为真实产品创作中有时间限制的第一阶段。Lead 在大规模实现前明确用户问题、目标用户、替代方案、证据、假设、差异化、可行性风险、最小可用版本和可衡量的成功标准。

实验性 Team 工具集提供 `spawn_user_tester`。Lead 提供唯一测试者名称和普通用户可见的应用入口。该工具始终使用已配置的 fresh Provider，固定 teammate 描述，并构造一项中性评估任务，禁止访问源码、仓库、路线图、开发者讨论和其他 Agent 的既有结论。评估者自由探索应用，并报告其推断的用途、有价值之处、使用阻力、信任问题、继续使用意愿、替代风险和三项优先改进。报告分别陈述观察、感受和建议修改。任务最多允许十二次工具调用；入口不可访问时只做一次简单重试，随后提交限制报告，并明确禁止寻找凭据和绕过认证。

Web Team 面板首先以克制的摘要展示总体状态、当前 ready 或 active task、已完成任务数量、活跃成员数量，以及是否有问题需要用户查看。摘要下方仍保留 roster 与 task 详情。

Fresh conversation history 提供信息隔离，而不是技术性 confinement。Teammate 仍共享部署与工作目录。需要强制隔离的部署使用沙箱化的纯 UI Provider；策略要求无法访问应用的评估者报告该限制，而不是检查实现文件。

## 考虑过的替代方案

**只为普通 `spawn_teammate` 工具提供建议提示。** 这种方式仍允许 Lead 加入产品意图、规定工作流和偏好结论，因此不同调用不能保持净室条件。

**为了方便而 fork 父对话。** Fork 会携带使首次用户评估产生偏差的产品理由和既有发现，因此专用工具始终选择 fresh Provider。

**把评估者当作安全沙箱。** 提示限制无法约束文件系统或进程工具。该功能明确其信息保证，并把技术性 confinement 留给拥有工具和执行环境的 Provider。

**把每条诊断和 Agent 状态变化作为面板摘要。** 原始活动会让正常调查看起来像产品故障。摘要先展示可操作的项目状态，同时保留详细 roster、诊断和 task 供用户检查。

## 后果

Lead 可以在投入实现成本前质疑产品价值，并且无需传递项目历史即可安排可重复的首次用户评估。专用 schema 会增加每次 Team member 请求的提示和工具 token 成本，更丰富的 Flash-first 指令也会在选择该 Profile 时增加提示成本。固定动作上限防止入口故障膨胀为凭据或端点探索。单个合成用户仍是弱证据：高成本决策需要重复的独立观察或真实用户证据。聚焦的工具测试固定 fresh 路由和提示内容；Client 测试固定克制摘要，组装后的 Web 快照覆盖完整面板。
